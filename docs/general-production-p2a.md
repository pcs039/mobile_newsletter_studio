# 일반 제작 P2 A 수동 음성과 프로젝트 폰트 보강

2026년 11월 1일. 기준은 고정 Staging `51537b5`와 P1 문서 커밋 `dc74bbd`다. P2-B 신규 발행호 제작과 R1-B는 실행하지 않는다.

## 수동 음성 연결

기존 `updateProjectAudioArticleLink`는 기존 연결을 두 번의 PATCH로 정리한 뒤 음성 메타데이터와 기사 연결을 각각 갱신했다. 중간 오류 시 일부 요청만 반영될 수 있었고, 음성 파일 연결과 기사 `audio_source` 선택도 분리되어 있었다. 기존 기사 저장 RPC는 블록·링크 저장 계약까지 포함하므로 수동 음성 연결용으로 재사용하지 않는다.

새 `manage_newsletter_manual_audio_link` 함수 하나가 다음을 한 트랜잭션에서 수행한다.

- 서버가 확인한 프로젝트·호출자와 같은 프로젝트의 업로드 음성/기사만 허용한다. 서비스 역할만 실행할 수 있으며 사용자·담당자도 DB에서 재확인한다. 프로젝트 비밀번호 접근은 기존 API 인증을 유지한다.
- 변경 요청에서만 프로젝트 → 기사 → 음성 순서로 잠근다. GET은 행 잠금 없이 단일 SQL/MVCC 스냅샷으로 권한·파일·참조 관계·revision을 함께 읽는다. 프로젝트의 음성 연결 정보와 선택 파일의 메타데이터를 포함한 revision을 조회하고 저장 시 CAS로 비교한다. 다른 음성·기사의 변경도 보수적으로 충돌 처리할 수 있다.
- 기존 양방향 연결 정리, 새 연결, `audio_source=uploaded`, 대본·검수 정보 저장을 함께 커밋한다. 실패하면 모두 롤백한다. 해제 시에는 해당 수동 연결만 정리한다.
- AI 음성이 선택된 대상 기사 또는 TTS 처리 중인 기사는 새 수동 연결을 거절한다. AI에서 수동으로 바꾸려면 작성 화면에서 먼저 명시적으로 변경한다. 기존 `ai_audio_id`, TTS 상태와 파일은 변경하지 않는다. 이전 수동 참조를 해제해도 선택된 AI 음성을 끄지 않는다.
- 생략된 대본·검수 필드는 유지한다. 불일치한 기존 양방향/다중 연결은 자동 복구하지 않고 충돌로 안내한다. 파일·구버전 메타데이터 삭제는 하지 않는다.

멱등성은 **요청한 연결과 명시한 메타데이터가 이미 동일하면 UPDATE 없는 성공**으로 구현한다. 별도 요청 이력 테이블이나 영구 receipt는 만들지 않는다. 이후 다른 상태로 바뀌었다면 오래된 revision으로 되돌릴 수 없다. 새로운 편집 요청과 구별되는 영구 요청 이력 조회 기능을 제공하는 것은 아니다.

기존 `/api/project-audio-links`에 인증된 GET 상태 조회를 추가하고 POST는 새 RPC만 호출한다. 예전 다중 PATCH fallback은 제거한다. RPC가 설치되지 않으면 503으로 닫힌다. UI는 상태를 먼저 읽고 저장 중 중복 클릭을 막으며, 응답 유실 시 입력을 잠그고 사용자가 같은 payload로 결과를 확인하게 한다. 자동 재시도는 없다. 충돌 시 초안을 남기고 명시적인 최신 상태 불러오기를 제공한다. 오류에 서버 키나 DB 원문 오류를 전달하지 않는다.

보호 범위는 이 수동 연결 작업의 CAS와 트랜잭션이다. 일반 기사 편집 전체를 새 revision 저장 시스템으로 바꾸지는 않았다. 다른 편집 화면과 병행할 때는 최신 저장본을 다시 불러온 뒤 음성 방식을 변경한다.

## DB 적용 조건과 P2 B 판정

SQL 초안은 `supabase/schema_v1_46_manual_audio_links.sql`이다. 변경 범위는 서비스 전용 함수 1개와 해당 함수의 실행 권한, PostgREST schema reload다. 새 테이블·컬럼·인덱스·데이터 backfill은 없다. 기존 스키마 중 v1.43의 `tts_generation_state` 등을 사전 검사하며 승인용 세션 설정 없이는 중단한다.

**코드·격리 구현은 완료했지만, 현재 고정 Staging에서 P2-B 신규 제작을 시작하는 판정은 보류한다.** 다음의 승인·적용이 필요하다.

1. Staging `mvrkpmffuhcqwisqvpqi`의 신원·선행 컬럼·역할을 재확인한 뒤, 해당 DB에만 v1.46 적용 승인을 받는다. 이번 작업에서는 적용하지 않았다.
2. 승인된 코드 SHA를 Staging 전용으로 적용한다. 신규 브랜치의 자동 Vercel 배포는 `vercel.json`에서 비활성화했다. 고정 Staging·Production·기존 PR은 변경하지 않는다.
3. 인증된 일반 수동 음성 GET과 권한·RPC 상태를 확인한다. 함수가 없거나 오류가 있으면 수동 저장을 막으며 이전 PATCH 경로로 돌아가지 않는다.
4. 별도 P2-B 쓰기 승인 후 신규 테스트 발행호에만 생성·저장·업로드·연결 검증을 진행한다. 기존 화성시 7건과 정상 자산은 대상에서 제외한다. 공식 발행·외부 공개는 별도 범위다.

적용 전에는 데이터 복구 작업이 없다. 적용 후 문제가 생기면 수동 연결 쓰기를 중단하고 상태를 읽어 확인한다. 코드 복귀 시 함수는 남겨도 기존 데이터에 자동 작용하지 않는다. 함수 제거가 필요하면 새 호출자가 없는 것을 확인한 뒤 별도 승인으로 수행한다. 정상 연결이나 파일을 되돌리기 위해 임의 삭제·재생성을 하지 않는다.


## PR 292 최종 동시성 검증

기준 `11fddc2`의 GET은 원문을 수정하지 않으면서 프로젝트·모든 기사·음성에 FOR UPDATE를 사용했다. 이 잠금은 읽기에는 필요하지 않았으며 편집과 음성 연결을 불필요하게 막을 수 있었다. GET만 잠금 없이 한 SQL statement에서 검증과 revision을 계산하도록 보정했다. 여러 SELECT로 단순 분리하여 변경 전후 데이터를 섞지 않는다. 관계의 AccessShareLock은 정상 SELECT 잠금이며 제거 대상이 아니다. 저장의 프로젝트 단위 CAS와 기존 강한 잠금 범위는 유지한다.

| 경로 | 순서와 경합 처리 |
| --- | --- |
| 수동 음성 GET | 단일 MVCC 조회. 행 잠금·RowShareLock·RowExclusiveLock 없음. READ ONLY 트랜잭션에서 실행 가능 |
| 수동 음성 변경 | 프로젝트 UPDATE → 기사 UPDATE → 음성 UPDATE. 선행 작성·TTS 커밋을 기다린 뒤 새 상태에서 CAS 재검사 |
| 기존 기사 저장 v1.38 | 프로젝트 UPDATE → 해당 기사 UPDATE → 블록·링크 저장 |
| 기존 TTS v1.43 | 프로젝트 SHARE → 해당 기사 UPDATE → 블록 SHARE → 완료 시 과거 음성 UPDATE |

실제 Staging의 기사 저장·정렬·TTS claim/complete/finish 함수 본문은 이 테스트가 읽은 저장소 버전과 해시가 일치했다. 테스트는 이 기존 함수들을 새 로컬 PostgreSQL의 합성 데이터에 설치해 실행했다. 실제 TTS 요청이나 MP3·Storage 작업은 없다.

두 개 이상의 독립 PostgreSQL 연결에서 다음을 추가 확인했다.

- 읽기 트랜잭션이 열린 동안 수동 저장이 진행되며 GET은 쓰기 행 잠금을 유지하지 않는다.
- 실제 기사 저장 중 GET은 기존 커밋 상태를 읽는다. 저장 커밋 뒤 기다리던 수동 요청은 stale 충돌, 저장 롤백 뒤에는 원래 revision으로 수동 저장이 가능하다.
- 수동 저장 → 기사 저장, TTS 완료 → 수동 저장, 수동 저장 → 다른 기사의 TTS 완료 순서에서 정상 직렬화된다. 수동·AI 연결을 보존한다.
- 의도적으로 음성 → 프로젝트의 역순 잠금을 잡은 합성 작성자는 PostgreSQL 교착 검출로 한 트랜잭션이 중단된다. 중단된 트랜잭션의 변경이 남지 않고 생존 트랜잭션의 연결은 일관된다.
- REPEATABLE READ의 오래된 작성자는 직렬화 오류로 중단되며 다른 연결의 커밋을 훼손하지 않는다.

정상 저장 경로에서 교착은 재현되지 않았다. 임의의 역순 작성자까지 교착 불가능하다고 보장하지는 않는다. 명시적 SQLSTATE 40P01/40001은 전체 트랜잭션이 중단된 것으로 분류해 HTTP 409와 최신 상태 조회를 안내한다. 네트워크·응답 본문 유실은 기존 unknown 및 동일 payload 확인 정책을 유지하며 자동 재실행하지 않는다. 일반 기사 편집기의 음성 방식 필드 변경까지 새로운 CAS 계약으로 바꾸지는 않았으므로, 음성 방식 변경은 최신 편집 화면에서 수행한다.

## 승인 후 적용과 복귀 순서

적용 SQL은 `supabase/schema_v1_46_manual_audio_links.sql`이며 SHA-256은 `101199002be4eaefba59005cc7c4944eca40dc399c1d2b89063d17d72492ab6e`다. 코드 후보는 이 문서를 포함한 PR #292 최신 head이며 정확한 배포 후보 SHA는 PR 설명과 완료 보고에 기록한다. 기존 Staging SHA는 `51537b51176b9427368c6705a2cf4549872fe5eb`다.

1. **전환 중 수동 연결 저장을 일시 중지한다.** 기존 열린 편집 탭·이전 Preview 직접 주소에서는 수동 저장을 하지 않는다. 구버전 서버의 쓰기를 새 RPC가 자동 통제하지는 않으므로 승인된 고정 도메인만 사용한다. 이전 Preview는 기존 접근 보호를 유지하고 필요 시 별도 승인으로 사용을 종료한다.
2. **DB 함수 적용:** 정확한 Staging ref·함수 미존재·선행 조건과 기준 digest를 다시 읽는다. 해당 DB의 postgres 권한과 같은 세션에서 `SET app.manual_audio_schema_target='explicitly-approved';` 뒤 위 SQL 파일을 적용한다. 테이블/컬럼/기존 함수/데이터를 변경하지 않는다. 새 함수 signature·본문·owner·search_path·service_role 전용 ACL과 PostgREST reload를 조회 확인한다. 이 단계에서는 앱 코드를 바꾸지 않는다.
3. **Staging 전용 배포:** 승인된 PR #292 최신 head만 고정 Staging으로 반영한다. main/Production이나 #290~#291을 병합하지 않는다. Vercel Preview/staging·Supabase ref·Ready·도메인 및 정확한 SHA를 확인한다. DB 오류 시 코드 배포를 중단한다.
4. **인증된 GET:** 기존 관리자 세션에서 기존 업로드 파일의 `/api/project-audio-links?projectSlug=canva-e2e-test&audioId=…`를 읽어 200·revision·대본/연결 상태를 확인한다. 아직 POST 연결·교체·해제는 하지 않는다. 이전 클라이언트의 revision 없는 저장은 새 API가 400으로 차단하며 과거 PATCH fallback은 없다.
5. **권한 및 오류:** 미인증 GET 401, 비담당 사용자 403, 존재하지 않거나 타 프로젝트인 음성의 인증 GET 404를 확인한다. 관리자가 다른 프로젝트에도 권한이 있을 때는 존재 여부와 프로젝트 불일치를 구분한다. 누락 RPC 503 및 40P01/40001→409는 격리·모의 테스트 결과를 사용한다. 오류 재현을 위해 Staging 함수를 삭제하거나 교착/장애를 유발하지 않는다.
6. **불변 비교:** 위 8개 영역의 digest·시연 기사 7건과 기존 검증용 2건·음성/참조 상태를 적용 전과 비교한다. 함수 정의/ACL 변경만 의도한 차이로 인정한다. 일치 확인 후에도 P2-B 프로젝트 생성·업로드·연결·발행은 별도 승인까지 하지 않는다.

실패 시 추가 쓰기를 중단한다. DB 적용 실패는 파일 전체 transaction이 롤백되어야 하며 부분 성공을 추정해 재적용하지 않는다. 앱 배포/GET 검증 실패 시 고정 Staging을 위 `51537b5`로 복귀할 수 있으나 **구버전 수동 저장은 재개하지 않는다.** 새 함수는 남겨도 호출하지 않으면 데이터에 작용하지 않으며, 기존 필드를 사용하는 reader는 기존 연결을 계속 읽을 수 있다. 정상 자료를 되돌리기 위한 파일 삭제·음성 재생성은 없다. 함수 제거는 신규 호출자가 없음을 확인한 뒤 별도 승인으로 한다.
